----Клиент-серверная архитектура
    Клиент-Бэкенд-Сервер(БД)
    HTTP - протокол передачи данных
    Стек Клиента:
        - web: JS
        - iOS: Swift
        - Android: Kotlin
    Стек Бэкенда:
        - c++
        - c#
        - python
        - java
        - scala
        - go
        - JS
    Стек БД:
        - Postgres
        - MySQL
        - Redis
        - MongoDB
    1. Клиент отправляет HTTP-запрос (ручка, метод, хэндлер, запрос, эндпоинт) на сторону Бэкенда
    2. Бэкенд отправляет SQL-запрос на сторону БД
    3. БД отправляет данные на сторону Бэкенда
    4. Бэкенд отправляет HTTP-ответ на сторону Клиента

----HTTP-запрос
    URL: (сама ссылка запроса, обязателен)
        https://meduza.io:443/api/w5/screens/news
        протокол - https (secured)
        Домен (хост) - meduza.io (до : или до /)
        Порт - 443 (по дефолту https - 443, http - 80) (от : до /)
        Путь - api/w5/screens/news (от / до ?)
        Квери - от ? до # в формате название=значение, разделяются &; может быть несколько; ограничение в 2048 знаков
        Якорь - от #; может быть только 1

    Headers: (свойства запроса и Клиента, обязателен)
        Host: https://meduza.io
        Accept: text/html
        type: Postgres
        Content-Type: application/json
        User-Agent: Mozilla/5.0 (Windows NT 6.1; WOW64)
        Accept-Language: RU, EN
        Accept-Charset: UTF-8
        Cookie: sessionid=FOCDNKIBFOJP

    Body: (информация о запросе, необязателен)
        [
            {},
            {},
            {},
            {}
        ]

----HTTP-ответ
    Status code: (статусы ответов)
    100-199 - информационные
    200-299 - успешные
    300-399 - перенаправления
    400-499 - ошибки Клиента
    500-599 - ошибка БД

    Headers: (свойства ответа и сервера)
    Content-Type: application/json
    Server: Microsoft-IIS/7.5
    Set-Cookie: sessionid=FOCDNKIBFOJP; expire=30d;
    Date: Sun, 04 Aug 2013 13:33:59 GMT
    Content-Length: 8434

    Body: (информация ответа)
    [
        {},
        {},
        {},
        {}
    ]

----Архитектурный стиль REST
    Возможные форматы в Body:
    - данные в формате JSON
    - данные в формате XML
    - Файл
    - HTML

    Типы запросов: 
    - GET (Получение данных) - идемпотентный - запрос для получения данных из БД - нет body
    - DELETE (Удаление данных) - идемпотентный - запрос для удаления данных из БД - есть body
    - POST (Отправка данных) - неидемпотентный - запрос для отправки данных в БД - есть body
    - PUT (Изменение данных) - идемпотентный - запрос для изменения данных в БД - есть body
    Редкие:
        - CONNECT - неидемпотентный - установка "туннеля" к серверу
        - OPTIONS - идемпотентный - параметры соединения
        - PATCH - идемпотентный - частичные изменения
        - TRACE - идемпотентный - тестовое сообщение
        - HEAD - идемпотентный - аналог GET
    
    Идемпотентность - свойство возвращать всегда один и тот же ответ

----JSON - формат данных
    JSON использует только 6 типов данных
    1. Строка - "текст"
    2. Число - 123
    3. Булеан - true/false
    4. null
    5. Массив - ["элемент 1", "элемент 2", "элемент 3"] - массив строк
    6. Объект - свойство, поле, ключ - всегда строка; значение - любое
    {
        "свойство": значение
    }

    Пример объекта:
    {
        "name": "iphone 13", (string)
        "price": 999, (number)
        "5g": true (boolean)
        "colors": ["white", "blue", "red"] (array)
    }

----XML - формат данных
    XML использует только теги, более защищённый формат, используется чаще в банках и других структурах требующих надёжности
    <тег>значение</тег>

    Пример тега XML:
    <bag>
        <laptop>macbook</laptop>
        <wallet>tinkoff</wallet>
        <id>passport</id>
    </bag>

    То же самое в JSON выглядит как:
    {
        "bag": {
            "laptop": "macbook",
            "card": "tinkoff",
            "id": "passport"
        }
    }

----Протоколы:
    HTTP-протокол:
        REST:
            Запросы:
                GET,
                POST,
                DELETE,
                PUT
            Body:
                JSON
                XML
                HTML
                Файл
        gRPC,
        graphQL - появляется звено между Клиентом и Бэкендом. 
        1. Клиент посылает всего 1 запрос в звено
        2. Звено распределяет его на несколько запросов в Бэкенд
        3. Бэкенд возвращает ответы на несколько запросов в звено
        4. Звено аккумулирует все ответы в один и отправляет в Клиент
        В итоге для Клиента есть условно один запрос и один ответ, который возвращает всё что нужно

    SOAP:
    Нет специального архиктектурного стиля
    Только один тип запросов
    В body только XML

----DevTools
    Вкладка Elements - работа с визуалом страницы, проверка шрифтов, цветов, картинок и т.д.
    Вкладка Console - показывает ошибки и предупреждения JS, можно вводить команды JS для тестирования
    Вкладка Sources - просмотр исходного кода фронта
    Вкладка Network - самая полезная для QA, просмотр всех запросов и ответов на запросы, статусы ответов, фильтры, throttling (имитация медленного интернета)
    Вкладка Performance - запись и анализ производительности
    Вкладка Memory - поиск утечек
    Вкладка Application - можно найти куки

----API - набор правил, протоколов и инструкций, который позволяет разным программам и сервисам общаться и обмениваться данными друг с другом
    Простыми словами API - контракт, который предоставляет программа "Ко мне можно обращаться так и так, я обязуюсь делать то и это"

----timestamp - использование формата времени в секундах прошедших в 1.01.1970 00:00:00

----Пагинация - распределение большого количества данных по страницам
    Пример: после отправки запроса на поиск телефона в Авито, он возвращает 100000 вариантов, но выдаёт только 50 вариантов на одной странице

----Postman - сервис для работы с HTTP-запросами и HTTP-ответами
    Использование коллекций
    Использование переменных {{}}
    Создание запроса:
        тип запроса
        параметры url (протокол, домен, порт, путь, квери, якорь)
        параметры header (в основном автоматически)
        параметры body
    Просмотр и работа с ответами
    Удобное создание автотестов через Snippets
    Интеграционное тестирование между запросами и ответами

----Виды тестирования
    По позитивности: (субъективно)
        - Позитивное - валидные, существующие данные
            Пример: правильный логин, правильный пароль, число в пределах возможных значений и т.д.
        - Негативное - невалидные, несуществующие данные, использование системы нетипичным образом
            Пример: неправильный логин, использование чисел вместо текста, использование значений вне возможных границ
    По функциональности:
        - Функциональное - ручное тестирование бизнес-требований, логики, ТЗ, АПИ
        - Нефункциональное:
            - Удобство - UX/UI
            - Нагрузочное - RPS - единица измерения Request Per Second
            - Стресс-тестирование - использование нагрузки много большей чем обычно
                Нагрузочное и стресс тестирования делаются:
                    1. Яндекс.Танк
                    2. Jmeter
            - Безопасность - тестирование безопасности (обычно делают специалисты, а не тестировщики)
                - SQL-инъекции 
                - пентест 
            - Требования - тестирование документации, ТЗ
                Тестирования на:
                    - Полнота - требование описывает все необходимые аспекты функциональности, включая обработку ошибок и граничные случаи
                        Неправильно: "Пользователь должен ввести пароль"
                        Правильно: "Пользователь должен ввести пароль длиной от 8 до 32 символов, содержащий как минимум одну цифру и одну заглавную букву..."
                    - Однозначность - требование имеет только одно возможное толкование, не содержит расплывчатых формулировок
                        Неправильно: "Система должна быстро загружать данные"
                        Правильно: "Система должна загружать список товаров менее чем за 2 секунды при скорости интернета 50 Мбит/с"
                    - Непротиворечивость - требование не конфликтует с другими требованиями в рамках системы
                        Пример: В одном месте кнопка "Сохранить должна быть синей", в другом "Все кнопки должны быть зелёными"
                    - Необходимость - требование отражает реальную потребность пользователя или бизнеса, а не чьё-то субъективное мнение
                        Пример: "На главной странице должен быть мигающий баннер с котиками" необходимо только если это ключевая бизнес-ценность
                    - Осуществимость - требование может быть реализовано в рамках заданных ограничений (бюджет, время, технологии)
                        Пример: "Приложение должно определять настроение пользователя по камере с точностью 99,9%" неосуществимо для стандартного коммерческого проекта с ограниченными сроками и бюджетом
                    - Тестируемость - требование можеть быть объективно проверено тестированием. Результат должен быть да/нет
                        Неправильно: "Интерфейс должен быть удобным"
                        Правильно: "Новичок должен выполнить задачу Х не более чем за 3 клика и за 30 секунд после прохождения onboarding"
                    - Атомарность - требование описывает одну законченную функцию или её часть, не объединяя несколько независимых функций
                        Неправильно: "Пользователь должен ввести логин, пароль и нажать кнопку "Войти" после чего система должна отправить приветственное письмо"
                        Правильно: "Аутентификация пользователя" и "Отправка приветственного письма"
                    - Корректность - требование не содержит фактических и грамматических ошибок, соответствует предметной области
                        Неправильно: "При вводе промокода предоставляется скидка 15$" - валюта может быть ₽
                        Правильно: "При вводе промокода предоставляется скидка 15%"
                    - Приоритезированность - требование имеет обозначенный уровень важности (Must Have, Should Have, Could Have)
                    - Прослеживаемость - требование имеет уникальный идентификатор, по которому можно отследить его связь с тест-кейсами и кодом
            - Инсталляционное:
                - Установка
                - Удаление
                - Обновление
    По понимаю задачи:
        - Black-Box - тестирование без необходимости просматривания кода
        - Grey-Box - тестирование с определённым уровнем знания кода
        - White-Box - тестирование с полным пониманием работы кода 
    По автоматизации:
        - Ручное
        - Автоматизированное:
            - юнит-тесты (пишут разработчики)
            - автотесты (пишут тестировщики)
    По разработке:
        - Бэкенд - Postman
        - Web - DevTools
        - Мобильные приложения - Charles
    В зависимости от исполнителей:
        - Альфа - внутреннее (команда, сотрудники)
        - Бета - внешнее (малый процент внешней аудитории)
    По степени подготовки:
        - По документации (имеющейся)
        - Исследовательское/Интуитивное/Здравый смысл - документации нет, но есть открытые требования (закон, лучшие практики, общепринятые методики и т.д.)
    По уровням:
        - Интеграционное/е2е/системное - тестирование нескольких модулей вместе или всей цепочки
        - Модульное - тестирование одного компонента, аще всего в юнит тестах
    По длительности:
        - регресс - проверка что новый функционал не сломал существующий, никогда не в проде
        - смоук - выжимка самых критичных кейсов как правило на 5 минут как правило на проде
    
----Баг-репорт - документации о дефекте
    Среда создания:
        - Яндекс.Трекер
        - Jira
    Состав и заполнение: (по Яндекс.Трекеру)
        -Summary (Заголовок) - основные моменты "Что? Где? При каких условиях?"
            [bug][web][прод] Некликабельная кнопка покупки на сайте в слайдере на втором слайде
                [bug] - указание что это баг
                [web] - указание что баг в вебе
                [прод] - указание что баг в проде, а не в тесте
        - Description (Описание) - описание дефекта (больше информации)
            #### Описание
            Некликабельная кнопка покупки на сайте в слайдере на втором слайде

            #### Шаги воспроизведения
            1. Открыть сайт www.ggogle.com
            2. Пролистнуть слайдер на второй слайдер
            3. Нажать купить
                
            #### Текущий результат (Фактический результат) (слова, скриншот, скринкаст)
            Кнопка покупки некликабельна

            #### Ожидаемый результат (слова, скриншот, ссылка на макет)
            Кнопка покупки кликабельна и позволяет купить товар

            #### Окружение (билд - версия ПО, если знаем; ОС; Браузер - какой, версия)
            Браузер Chrome версия nnnnnn
            Браузер Firefox версия nnnnnn

            #### Тестовые устройства (описание устройств, диагональ для мобильных)
            Macbook 16 (Monterey)

            #### Ручка* (чаще для баг-репорта на бэкенд) (cURL)

            #### Аналитика* ** (сколько пользователей затрагивает баг, аналитика кого затрагивает по Яндекс.Метрике)
            Статистика пользователей кого зааффектила проблема

            #### Документация* ** (ссылки на документацию)
            Ссылка на документацию по фиче

            #### Логи (kibana)* ** (ссылки на логи)
            Ссылки на логи в момент воспроизведения проблемы

            #### Slack* ** (ссылки на сообщения о баге Slack) (Slack - платный (для компании) мессенджер для работы)

        Assignee - тот на кого заводится репорт
        Priority - приоритет бага

            Minor - незначительный

----Техники тест-дизайна 
    Тест-дизайн - процесс, который помогает сгенерить больше разных тест-кейсов
    Техники:
        - Юзер Стори - как бы функционалом воспользовался разный пользователь (старый, богатый, новый пользователь и т.д.)
        - Pairwise (Попарное-тестирование, комбинаторика) - использование пар для ускорения тестирования (фильтры/значения и т.д.)
            удобно использовать открытые ресурсы для создания списка пар (pairwise.teremokgames.com и другие)
        - Разбиение на классы эквивалентности
            Классы эквивалентности - множества значений, которые при тестировании дают один результат
            Пример: 0-10[5], 11-20[15], 21-30[25]
        - Анализ граничных значений
            Граничные значений - минимум и максимум значения на стыке классов эквивалентности и +/- 1 шаг
            Пример: -1, 0, 1   9, 10, 11, 12    19, 20, 21, 22 и т.д.

----Kibana

----Тест-кейс - чёткое описание действий, которые необходимо выполнить для проверки функционала в строгом формате
    В тест-кейсе не должно быть фактического результата
    Все тест-кейсы ведут в TMS системах
    Пример:
        Название: Авторизация через Google
        Приоритет: Критичный
        Предусловие (необязательно): Установить приложение Едадил
        Шаги воспроизведения: 
            1. Открыть приложение Едадил
            2. Нажать "Авторизоваться"
            3. Выбрать авторизацию через Google
            4. Ввести логин и пароль от Google и дать разрешение
        Ожидаемый результат: Произойдёт авторизация в Едадиле
        Постусловие (необязательно): Разлогиниться

----Чеклист - список пунктов не в строгом формате со смыслом записать и структурировать все проверки с чекбоксами
    Пример - приложение с тремя кнопками "Американо", "Капуччино" и "Сахар", которое делает заказ кофе
    Сахара может быть максимум 5 порций
        Сайт/мобильное приложение:
            Функциональное тестирование:
                По позитивности:
                    Позитивные:
                        - Американо
                        - Капуччино
                        - Капуччино с сахаром
                    Негативные:
                        - Что если сахар выбрать без кофе?
                        - Как ведёт себя приложение, если кофемашина отключена от сети?
                        - Если нет зёрен?
                        - Если нет сахара?
                        - Если нет воды?
                        - Если нет молока?
                        - Если сахара осталось на 1 порцию, а нужно 2?
                        - Проверка работы на расстоянии
                        - Заказываем кофе ещё раз пока он уже готовится
                        - Можно ли отменить свой выбор?
                        - Что произойдёт если нажать на кнопку назад на телефоне на разных этапах заказа кофе?
                Кнопки: (универсальные проверки для всех кнопок)
                    - В каких случаях активна, а в каких заблокирована?
                    - Управление с клавиатуры (Tab, Enter) только длч web
                    - Уходит ли запрос на Бэкенд?
                Инпуты: (универсальные проверки для всех инпутов)
                    - Плейсхолдер
                    - Пустое значение
                    - Пробел
                    - Обязательность
                    - Одно слово
                    - Два слова
                    - Все заглавные
                    - Спецсимволы и смайлы
                    - Все строчные
                    - Одно очень длинное слово без пробелов
                    - Ссылка
                    - Разные языки
                    - Если число, то проверить десятичное
                    - Ноль
                    - Отрицательное значение
                    - 0.0 или .0 или 00
                    - Правила валидации (имейл с @, номер с +7 и т.д.)
                    - Управление с клавиатуры
                    - Вставить из буфера обмена
                Классы эквивалентности:
                - 0
                - 1-5
                - от 5
                Граничные значения:
                - 0, 1

                Попарное тестирование:
                - Американо + Сахар

                    - Нагрузочное

----TMS (Test Management System) - системы для работы с тестовой документацией
    Примеры:
        - TestRail - самая популярная в мире
        - Test It - русский аналог TestRail
        - Qase.io - сервис от русских создателей направленный на западный рынок, но не сильно популярный
        - Zephyr - дополнение к Jira
        - Яндекс.Пальма - внутренний сервис для Яндекса
    SUIT - группа тест-кейсов объединённые по какому-либо принципу (Регресс фронт SUIT, регресс бэк SUIT, смоук SUIT и т.д.)
    RUN - любой запуск тестирования, может содержать несколько SUIT (проверяю фронт и бэк SUIT, в завтрашнем RUN проверю смоук SUIT)
    MILESTONE - более общие рамки тестирования  (тест версии, тест релиза и т.д.)

----Сниффер - ПО для работы с HTTP-запросами и ответами с мобильных устройств и с ПК
    Популярные снифферы: Charles, Fiddler, ProxyMan
    Функция Breakpoints - останавливает запрос и (или) ответ. В момент остановки их можно редактировать
    Функция Map Local - подставляет в body ответа JSON с локального хранилища вместо пришедшего

----Работа бэкенда с БД
    Чаще всего БД существует не в одном экземпляре в целях безопасности данных
    Существует одна Master DB и сколько угодно Slave DB
    В Master DB Бэкенд может делать запросы на чтение и изменение
    В Slave DB Бэкенд может делать запросы только на чтение
    Slave DB подгружает данные из Master DB каждый определённый компанией промежуток времени
    Виды БД:
        - Реляционные [SQL] (postgres, mySQL) - данные хранятся в разных местах и сообщаются друг с другом
        - Нереляционная [NoSQL] (redis, mongoDB) - данные хранятся в одном месте
